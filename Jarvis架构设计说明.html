01项目概览与协作四象限

Jarvis 不是又一个"聊天机器人"，而是一个协作式 AI 开发平台。它以 jarvis-ai-assistant（当前版本 7.1.0）为核心包， 能真正进入开发工作流：读代码、改代码、执行工具、管理上下文、沉淀经验，并在关键节点保持人工可控。

它的核心命题是：让 Agent 从「独自工作」走向「与众共事」。协作能力沿两个维度交叉展开 —— 人的维度（单人 vs 多人）与 Agent 的维度（单个 vs 多个），形成四种协作模式，Jarvis 完整覆盖全部四种：

协作模式一句话价值核心能力
单人单 Agent独当一面符号级代码理解、影响分析、无人值守、交叉验证、集成终端/编辑器
单人多 Agent一人驱动一个团队编排网络（YAML DSL）、Agent 间群聊/点对点通信、多面板同屏操作
多人单 Agent团队共享一个 AIJWT 多用户认证、ACL 权限组、共享协作、聊天室群聊
多人多 Agent分布式协作网络多节点多网关、跨节点通信、节点级运维、权限控制

多用户与协作能力仅通过 Web 接口提供；CLI 面向单人使用。另提供 Python SDK（from jarvis.jarvis_agent import Agent）供系统集成。

02总体分层架构

仓库三大件：src/jarvis（Python 核心，约 24 个子包）、daemon/（Go 本机守护进程）、 browser_extension/（浏览器扩展）。整体呈清晰的六层结构，调用自上而下、事件自下而上：

设计要点：每层职责单一 —— 内核（agent）、能力（tools）、领域智能（code_agent）、执行通道（daemon/扩展）、协作（gateway）各司其职，均通过统一接口（如 IGateway）与事件总线解耦，扩展面极广。

03Agent 内核与主循环

jarvis_agent/ 是整个系统的心脏。核心是 Agent 类与 AgentRunLoop：主循环采用 ARCHER 工作流 —— 模型输出携带 [MODE: XXX] 阶段标记（分析 / 编码 / 验证等），由循环解析并驱动阶段切换，把隐式工作流显式化。

关键机制

  • 模型分档调度：配置模型组（normal_llm / fast_llm / eval_llm），按任务复杂度自动切换，无需人工选模型。
  • 上下文压缩：Git 上下文、任务列表、近期记忆、关键信息、意图识别等多机制协同，保证长任务目标不漂移。
  • 主/支线任务分离：task_manager + task_list 让支线流程不污染主 Agent 上下文。
  • 会话管理：自动保存、手动恢复，退出可继续；AgentManager 负责生命周期，Web 模式通过注入 multiline_inputer / confirm_callback 替代终端交互。
  • Fork 子 Agent：sub_agent / sub_code_agent 默认继承父 Agent 完整上下文，零丢失传递。
# ARCHER 工作流的阶段标识示例（模型输出头部）
[MODE: ANALYZE]
正在分析 user/service.py 的登录验证逻辑……
[MODE: EXECUTE]
调用 edit_file 修改第 42 行……

04工具系统

jarvis_tools/ 用统一抽象承载 Agent 的全部能力：Tool 基类 + 注册表。工具协议分两代 —— v1.0（位置参数 func(arguments)）与 v2.0（关键字参数 func(**kwargs)），并按签名静态判定调用方式，避免误判； interactive=True 的工具（如虚拟终端）在原生并行调用时整批降级为串行。

class Tool:
    def __init__(self, name, description, parameters, func,
                 protocol_version="1.0", interactive=False): ...
    def execute(self, arguments: Dict) -> Dict:   # 统一返回 {success, stdout, stderr}
        ...

扩展方式：自定义工具放 ~/.jarvis/tools/ 即被注册；支持中心工具仓库（central_tool_repo）团队共享；MCP 工具（stdio / sse / streamable 三种传输）与原生工具统一纳入调度，无依赖时可并行调用。

05代码智能层（符号级理解）

这是 Jarvis 区别于"套壳"工具的核心壁垒。jarvis_code_agent/code_analyzer/db/ 基于 tree-sitter AST 解析 + SQLite 符号数据库 + 图遍历，精确回答"改这个函数会影响哪里"。

CodeAgent 的工程闭环

  • worktree 并行：worktree_manager 在独立 Git worktree 中并行开展多条修改线，互不干扰。
  • 变更后自动处理：after_change / code_agent_postprocess 自动跑格式化与静态检查（ruff、clang-tidy 等）。
  • 独立 Agent 验证：修改结果交由另一个 Agent 审查（code_reviewer），交叉验证降低单模型盲区。
  • 增强 diff 预览：diff_visualizer 按文件给出补丁摘要，人工确认后再落地。

06多 Agent 与分布式协作

协作能力围绕 Web Gateway 这一统一消息中枢构建：消息路由、群组管理、跨节点转发、鉴权。 Agent 之间通过 gateway_manager 工具互相通信 —— Agent 不仅是被管理的对象，更是管理的主体（"Agent 管理 Agent"的自组织协作）。

声明式编排

多 Agent 网络用 YAML 声明式定义，orchestration_loader 解析校验（type、working_dir 必填）， pipeline_runner 一键部署，前端多面板同屏可视（宠物大厅将每个 Agent 渲染为宠物精灵 + 节点拓扑层）。

# orchestration.yaml（示意）
agents:
  - name: coder
    type: code_agent
    working_dir: /workspace/project
  - name: reviewer
    type: agent
    system_prompt: "你是严格的代码审查者…"
relations:
  - from: coder, to: reviewer   # 修改完成后交由审查 Agent 验证

四个协作模式层层递进：单人单 Agent 是基础，单人多 Agent 是扩展，多人单 Agent 是共享，多人多 Agent 是终极形态。

07本机执行双通道

Agent 要真正"动手"而不依赖公网入口，Jarvis 设计了两条互补的本地执行通道：Go 守护进程管"本机系统"， 浏览器扩展管"真实浏览器"。两者均以出站 WebSocket 连接网关，无需开放端口、无需公网 IP。

风险提示：浏览器扩展申请 28 项权限，其中 Cookie / webRequest / proxy / browsingData 等 8 项为高敏感，叠加后等同于把浏览器（含全部登录态）完全交给 Agent，且设计上不做权限控制。清除浏览数据、卸载扩展、删除 Cookie 等操作不可逆，请仅在完全信任所连网关时启用。

08知识沉淀与记忆体系

Jarvis 的核心命题之一是"越用越聪明"。知识资产分三类，按问题类型索引，支持中心 Git 仓库团队共享：

资产机制价值
分层记忆标签化管理（短期 / 项目 / 全局），无向量计算，更轻量低成本长期记忆，jmo 可合并相似标签
方法论成功经验自动沉淀为可复用方法论，LLM 从候选中按相关性选取（可选 eval 模型打分）把一次成功变成次次成功
规则前期固定流程筛选，后期按需自主加载，确保规则被有效运用而非全部塞进上下文上下文友好，规则命中率更高

技能自动发现（SkillHub）

本地规则不足覆盖当前任务时，自动走"搜索 → 评估 → 安装 → 注册"闭环（jarvis_agent/skill_discovery/）： 按任务描述检索远程技能市场 → LLM 对比候选与任务需求给出采纳结论 → 自动下载安装并注册到规则体系 → 后续任务直接复用。 也可通过 auto_select_rule 工具手动触发。

插件机制：内核 + 插件包架构。config.yaml 支持的任意配置（工具 / 规则 / 方法论 / 模型 / Agent 定义 / 回调）均可打包为插件，安装后自动发现并注入 —— 无需改内核、无需重新部署。

09安全模型

层面机制
身份认证JWT 多用户体系（注册/登录/登出），bcrypt（12 轮）哈希；初始 admin 无密码登录后强制改密（must_change_password），支持 JARVIS_ADMIN_PASSWORD 预置
权限控制两层模型：系统级（角色）+ 资源级（Agent 访问控制 ACL，分组权限矩阵，节点级控制，持久化）
执行防护execute_tool_confirm 执行前确认；虚拟终端；关键节点人工介入；无人值守需显式开启
密钥安全share_secret_scanner 扫描共享内容防泄露；扩展 Token 仅存内存不落盘
通道安全daemon 本地 API 仅绑 127.0.0.1；扩展与节点经私钥/登录态鉴权；网关黑白名单（host:port 通配）

10部署架构

平台方式要点
Linux（主要）quick-install.sh 一键安装uv + Python 3.12，可选 rg/fd/fzf/tmux 增强
Windows 原生quick-install.ps1 / 手动 uv脚本依赖 Release 中内置的 Windows 依赖目录（deps 不进 git）；daemon install 走计划任务
Windows / 任意WSL2 / DockerWSL 最稳；Docker 镜像内置前端与 clang 工具链，默认 CMD 即启动服务
离线环境create_offline_package.sh支持 x86_64 / aarch64（Linux）

服务拓扑

  • Master 节点：jarvis-service run --gateway-host 0.0.0.0 --gateway-port 8000，网关默认 127.0.0.1:8000、前端默认 127.0.0.1:5173。
  • Child 节点：--node-mode child --master-url ws://master:8000 --node-secret …，经 WebSocket 反向连出，仅跑 Agent 不起前端；node-id 需唯一。
  • 守护进程：本地 API 127.0.0.1:17800；凭据可由网页推送或 jarvis-daemon login -gateway … -u admin 命令行注入。
Windows 注意：jarvis-service 的 install/start 子命令内部走 systemd（Linux 专属），在 Windows 上不会真正拉起服务 —— 请用 jarvis-service run 前台启动；而 jarvis-daemon 的 install/start 在 Windows 上走计划任务，可正常使用。

11架构评价：优势与风险

✅ 设计优势

  • 分层清晰：六层职责单一，接口与事件总线解耦，扩展面广。
  • 符号级理解是真壁垒：SQLite 符号库 + 图遍历的影响分析，不是提示词套壳。
  • 协作四象限全覆盖：从个人工具到分布式平台的完整路径，同类开源罕见。
  • 知识闭环：方法论 / 规则 / 记忆 + 技能自动发现，越用越强。
  • 本地可控：数据不出本机，双执行通道零公网依赖，Go daemon 零依赖单文件。

⚠️ 风险与改进空间

  • [MODE:] 文本协议偏脆弱：依赖模型严格输出格式，健壮性不如显式状态机，可逐步迁向结构化事件。
  • CLI 入口耦合偏重：jarvis.py import 链长；Web 后端薄、前端重（jarvis_service 仅 cli.py）。
  • 扩展权限过宽：浏览器扩展 28 项权限且不做权限控制，安全完全依赖用户信任。
  • Windows 支持有缺口：jarvis-service 的 install/start 未接入 WindowsTaskBackend（死代码），多用户常驻需自行兜底。
  • 版本口径：README 数据基于 v5.0.1，主版本已到 7.1.0，文档与代码存在滞后。
